# Starforge M5d (Packaging, documentation, browser tests, v0.1.0) Implementation Plan

> **For agentic workers:** implement this plan task by task with subagent-driven development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v0.1.0 per spec §12 and §14 M5:
- **Server binaries:** static `starforged` binaries for Linux x86_64 and aarch64 (musl, rustls).
- **OCI image:** an image bundling `git` (and OpenSSH for SSH remotes).
- **CLI distribution:** `starforge` via cargo-dist (shell installer, Homebrew, Windows MSI) and `cargo install`.
- **Documentation:** admin, user, and format documentation.
- **Browser tests (§13):** Playwright tests for the session viewer and the merge flow.
- **Release metadata:** version 0.1.0 and release notes that list migrations (§12).

**Architecture:**
- No server code changes, except:
  - the version;
  - whatever the musl build or the browser tests prove broken. Any such fix goes in its owning module, reported.
- New files:
  - `scripts/build-release.sh` (cargo-zigbuild cross builds, tarballs, SHA-256 sums);
  - `Containerfile` plus `packaging/entrypoint.sh`;
  - `dist-workspace.toml` (cargo-dist, CLI only);
  - `.github/workflows/{ci.yml,release.yml}`;
  - `docs/admin/*.md`, `docs/user/*.md`, and `docs/format/README.md` (index plus the bundle format);
  - `CHANGELOG.md`;
  - `tests/browser/` (Playwright, TypeScript) with `scripts/browser-tests.sh`.

**Tech Stack:**
- Build tools installed with `cargo install --locked`: `cargo-zigbuild` (uses the existing `~/.local/bin/zig`) and `cargo-dist`. These are build tools, not crate dependencies.
- `rustup target add x86_64-unknown-linux-musl aarch64-unknown-linux-musl`.
- podman for the image.
- Node 22 with `@playwright/test`, installed under `tests/browser/` and never in the Rust build.

**Spec:** §12 (distribution, configuration, upgrades), §5.5 (platforms; runtime `git` ≥ 2.38), §13 (browser tests), §14 (M5: packaging, docs), §1 (licenses per program).

**Deferred:** publishing to crates.io, Homebrew taps, and GitHub Releases. That needs credentials and a remote; this milestone makes everything publish-ready and verifies it locally.

## Global Constraints

- **Static binaries:** the x86_64 musl `starforged` must run on this machine and report `0.1.0`. `file` must report "statically linked" for both architectures. If a dependency needs a C toolchain beyond zig's `cc`, fix the build (features) rather than shipping a dynamic binary.
- **The OCI image:**
  - runs as a non-root user;
  - has `/data` as the only volume;
  - exposes 3000 and 2222;
  - contains `git ≥ 2.38`, `openssh-client`, and CA certificates.
  The entrypoint runs `starforged init` when `/data/starforged.toml` is missing, then `starforged serve`. The verification is `podman build`, then a run, then `curl /healthz` returning 200, then a `git clone` over HTTP from the container.
- **cargo-dist** covers ONLY `starforge-cli`; server crates set `dist = false`. Installers: shell, homebrew, and msi (MSI needs a WiX GUID block generated by `dist init`). `dist plan` must succeed locally. A local `dist build` of the shell installer for `x86_64-unknown-linux-gnu` must succeed.
- **`cargo install`:** the MIT OR Apache-2.0 crates (`starforge-format`, `starforge-redact`, `starforge-capture`, `starforge-cli`) get `publish = true`, descriptions, `repository`, `readme`, and versioned path dependencies. `cargo package -p starforge-format -p starforge-redact -p starforge-capture -p starforge-cli` must succeed. Server crates stay `publish = false`.
- **Documentation accuracy:** every config key, command, route, and default in the docs is checked against the code. Doc examples that are commands get exercised in a smoke script, `scripts/docs-smoke.sh`, which runs a fresh server through init → admin user create → repository create → clone → CLI login (device flow through the API) → push a Trail change.
- **Browser tests** are not part of `scripts/check.sh` (Node is optional for contributors). They run through `scripts/browser-tests.sh` and in CI. They must pass locally 3 times in a row.
- **Every commit:** fmt, clippy `-D warnings`, and workspace tests green on SQLite and `STARFORGE_TEST_PG=1`.

## Decisions this plan makes where the spec is silent

- **D1. Cross builds with zig.** `cargo-zigbuild` uses the installed zig as the musl C toolchain for rusqlite's bundled SQLite, ring, and zstd. Release profile: `lto = "thin"`, `codegen-units = 1`, `strip = true`.
- **D2. Image base:** `docker.io/library/alpine:3` (musl matches the static binary; `git` and `openssh-client` from apk) with `tini` as PID 1. The image tag is the version.
- **D3. Docs layout.**
  - **README:** an overview, a quick start, and links. The long feature sections move to `docs/user/` and `docs/admin/` unchanged in substance.
  - **`docs/admin/`:**
    - install;
    - configuration (a reference table of every key and its `STARFORGE__` override);
    - database;
    - reverse proxy and TLS;
    - SSH;
    - SSO and 2FA;
    - mirrors and import;
    - backup and restore;
    - upgrades and migrations;
    - doctor;
    - monitoring;
    - abuse controls;
    - site administration.
  - **`docs/user/`:**
    - getting started;
    - repositories and SSH keys;
    - Trails (changes, revisions, reviews, gates, merge);
    - sessions (CLI capture, privacy rules, viewer, export and import);
    - search;
    - orgs and teams;
    - API and webhooks.
  - **`docs/format/README.md`:** links the normative v1 docs and adds the export bundle layout.
- **D4. Release notes.** `CHANGELOG.md` gets a `## 0.1.0` section listing features by area and every migration `0001`–`00NN` with a one-line purpose, plus the upgrade note (forward-only; back up first).
- **D5. Browser tests** (`tests/browser/`, Playwright with Chromium only). A seeded server is started by the script from a fixture-building `starforged` test helper binary or setup commands.
  - **Session viewer:** the keyboard reaches the search box, results jump to `#turn-<seq>`, the split view switches commits through the JS enhancement, and collapsed tool calls expand.
  - **Merge flow:** sign in, open a Trail, the gate panel shows blocked, approve as a second user, the gate passes, merge with the selected method, and the Trail shows merged.
